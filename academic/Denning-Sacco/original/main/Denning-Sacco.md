## 1 Introduction

The Denning-Sacco protocol is a symmetric key-based authentication and key establishment protocol designed for use in networks with a single trusted server and multiple agents. It enables two agents (participants) to establish a secure session key for subsequent communication, where each agent shares a unique secret symmetric key with the trusted server but no direct shared keys exist between agents. The protocol leverages timestamps to ensure the validity and freshness of the session key, facilitating secure communication over insecure network channels.

## 2 Protocol Participants

- **A** : A participant that initiates the session key request process, aiming to establish a secure communication session with another participant (B).

- **B** : A participant that is the intended communication partner of A, receiving a ticket from A to obtain the session key and verify the communication validity.

- **S** : A trusted authority responsible for generating session keys, encrypting key-related information with the long-term symmetric keys shared with each agent, and facilitating secure key distribution between A and B.

## 3 Notation

When A initiates communication with B via the trusted server (S), the protocol uses the following terminology and security protocol notation:

- A and B: Identities used to identify the communicating participants.

- S: Identity of the trusted server that facilitates session key distribution.

- Ksa: A secret symmetric key shared exclusively between A and the server (S).

- Ksb: A secret symmetric key shared exclusively between B and the server (S).

- Kab: A fresh session key generated by the server (S) for secure communication between A and B.

- T: A timestamp generated by the server (S) to indicate the validity period of the session key Kab.

- {X}K: A message X encrypted with the symmetric key K, representing confidential data transmission.

## 4 Protocol Description

The Denning-Sacco protocol consists of three core message exchanges to establish the session key Kab between A and B. The detailed message flow is as follows:

Message 1: A → S: A, B  
Message 2: S → A: {B, Kab, T, {Kab, A, T}Ksb}Ksa  
Message 3: A → B: {Kab, A, T}Ksb

Here, A and B are two participants, and S is the server. A requests from the server a session key to communicate with B.
The server generates a new session key, Kab, and sends it to A, encrypted with the (symmetric) key shared between A and S. This message also contains a timestamp T, used to determine the validity of the new session key, and the ticket {Kab,A,T}Ksb.
A then forwards this ticket to B, who can decrypt it using the key Ksb shared between B and S, to obtain the new session key Kab, the name A of the intended communication partner, and the time T of the request.

## 5 Assumptions

This section defines the complete assumption space used to evaluate the goals
in Section 6. Conditions already represented by the flow model, including the
public attacker-controlled network and unbounded protocol sessions, are not
additional assumptions.

- **Disclosure of A's long-term key.** The analysis treats `Ksa` as an
  independent data-exposure dimension. In its normal state the attacker does
  not obtain `Ksa`; in the compromise state `Ksa` is disclosed to the attacker
  from the beginning of the run.
- **Disclosure of B's long-term key.** The analysis treats `Ksb` as a second,
  independent data-exposure dimension. In its normal state the attacker does
  not obtain `Ksb`; in the compromise state `Ksb` is disclosed to the attacker
  from the beginning of the run.

The three scenarios used below are the baseline with neither disclosure,
disclosure of `Ksa` alone, and disclosure of `Ksb` alone. The two disclosure
conditions are not combined in this analysis. Listing a goal in a disclosure
scenario means that the goal is evaluated there; it does not presume that the
goal holds.

## 6 Security Properties

The analysis poses exactly the following three security goals. A goal is a
question for formal verification and may be proved or refuted.

- **Session-key secrecy.** `Kab` is secret from the attacker and may be known
  only by the principals playing `A`, `B`, and `S` in the session.
- **B's non-injective agreement with A.** When `B` completes, `B` has
  non-injective agreement with `A` on the tuple `(A, B, Kab, T)`.
- **B's injective agreement with A.** When `B` completes, `B` has
  injective agreement with `A` on the tuple `(A, B, Kab, T)`.

Each of these three goals is evaluated in all three Section 5 scenarios: the
baseline, disclosure of `Ksa` from the beginning, and disclosure of `Ksb` from
the beginning.
