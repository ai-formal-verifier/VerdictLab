## 1  Introduction

This document describes the public-key authentication protocol of Needham and Schroeder [1],
applicable for two entities (A and B) that wish to authenticate each other over a hostile
network. The protocol has seven messages. Two of them are the key-distribution exchange
between the initiator and an authentication server, two more are the same exchange for the
responder, and the remaining three are the authentication handshake proper. All seven are
in scope for this specification, and this is the form SPORE records [2].

Neither party is assumed to hold the other's public key at the start of a run. Each obtains
the peer's public key during the run, from the authentication server, in a message the
server signs so that the key and the identity it belongs to cannot be separated. This is
what makes the server an integral part of the protocol rather than a preliminary to it.

The original publication notes that the four key-distribution messages "can be done away
with by A and B both having local caches of commonly used public keys" [1]. That cached
variant is a different deployment of the same protocol and is out of scope here; this
document specifies the seven-message form, in which the keys are fetched.

## 2  Protocol Participants

**A:** the initiator. It holds its own key pair (SKA, PKA) and the public signing key PKas
of the authentication server. It does not hold PKB. Needham and Schroeder require that
"A must obtain and store PKAS in a reliable way, so he is sure it is correct", since an
intruder who could substitute a value for PKas "could impersonate AS" [1].

**B:** the responder. It holds its own key pair (SKB, PKB) and PKas. It does not hold PKA.

**S:** the authentication server. It holds its own signing key pair (SKas, PKas) and the
public key of every principal it serves. Needham and Schroeder describe its store as a
database that "is indexed by name", holding items of the form `A : {PKA,A}SKAS`, with a
secure computation required "only when a new public key is registered" [1]. S generates no
fresh material and keeps no state between requests; it only vouches for a binding it
already holds.

Every principal that takes part is registered with S.

## 3  Notation

The following notation is used to describe the protocol steps:

- **PKA, PKB:** Public keys of A and B.
- **SKA, SKB:** Private keys of A and B.
- **PKas, SKas:** The authentication server's public and private signing keys.
- **A, B:** The identities of the two parties.
- **{X}K:** Encrypt message X using public key K.
- **{X}SKas:** Sign message X with the server's private key; anyone holding PKas can recover
  X and knows S produced it.
- **I_A, I_B:** Random numbers generated by A and B (Nonce), used to ensure session freshness
  and prevent replay attacks. SPORE writes these as Na and Nb [2].
- **MT:** The message type, the first field inside each encrypted handshake message
  (messages 3, 6 and 7). Each of these messages has its own MT value, given in its step.

## 4  Protocol Description

The letters A and B below name the initiator and responder in one illustrated session; they
do not define a permanently fixed pair of principals. When an initiator instance starts,
its intended peer identity is a per-session input naming a principal. Likewise, the
responder treats the claimed initiator in message 3 as its counterparty. The initiator uses
that same input in
message 1, checks it against the identity returned in message 2, and uses the returned key
in messages 3 and 7. Thus different initiator instances may be addressed to different
principals. Whether S has a registered binding for the selected identity is a separate
admission question: if no such binding exists, S cannot answer message 1 and that session
cannot proceed. In the honest run illustrated below the selected peer is B; in the Lowe
scenario of Sections 5 and 6 it is the registered principal I.

**Step 1: The initiator asks for the responder's public key**
A → S: A, B

A names itself and the principal it wishes to authenticate. Needham and Schroeder describe
this step as "A consulting the authentication server in the clear to find B's public key" [1].
The request is not protected; it carries no secret and its integrity is not relied upon.

**Step 2: The server vouches for that key**
S → A: {PKB, B}SKas

S looks up the public key it holds for the named principal and returns it signed together
with that principal's identity. A verifies the signature with PKas and takes the key from
it. Encryption here "is required not to ensure the privacy of the information but to ensure
its integrity": it "is important that A should be sure that he is getting PKB rather than
the public key of some miscreant", and "A knows that the name of the intended recipient, B,
was correctly communicated to AS because that name is returned in message 2.2" [1]. A
therefore checks that the identity inside the signed unit is the one it asked about.

**Step 3: Initiate the Request**
A → B: {MT, I_A, A}PKB, with MT = 1

A sends an encrypted message to B, identifying itself with its identity A and including a
fresh random number I_A. This message "can only be understood by B" and "indicates that
someone purporting to be A wishes to establish communication" [1]; B decrypts it with its
private key SKB and checks that MT = 1.

**Step 4: The responder asks for the initiator's public key**
B → S: B, A

Having decrypted message 3, B knows which identity claims to be talking to it, and requests
the public key for that identity.

**Step 5: The server vouches for that key**
S → B: {PKA, A}SKas

As in step 2, in the other direction. Message 5 "is encrypted for integrity, as was 2.2, not
for secrecy" [1]. B verifies the signature with PKas and checks that the identity inside is
the one it asked about.

**Step 6: Mutual Authentication and Random Number Exchange**
B → A: {MT, I_A, I_B}PKA, with MT = 2

B sends back an encrypted message containing I_A and the newly generated random number I_B,
using the public key it obtained in step 5. On receiving it, A decrypts with SKA, checks
that MT = 2 and that the returned value equals the I_A it sent.

**Step 7: Final Confirmation**
A → B: {MT, I_B}PKB, with MT = 3

A returns I_B under the public key it obtained in step 2. B checks that MT = 3 and confirms
that I_B is the value it generated. Needham and Schroeder call messages 6 and 7 the completion of a "double
handshake … to authenticate A and B to one another and to establish the time integrity of
the conversation" [1].

## 5  Assumptions

This section defines the complete assumption space for the Section 6 goals.

- **Peer-authentication admission.** The identity scope `peer_auth` has two
  possible admission states. In the closed state only the honest peers already
  represented by the model are registered. In the open state the attacker may
  register a recognised principal and an honest initiator may select that
  identity as its peer.

The analysis uses two scenarios: the closed-admission baseline and an
`admission_open` scenario in which `peer_auth` is open.

## 6  Security Properties

The following four goals are evaluated in both the closed baseline and the
open-admission scenario.

- **Secrecy of A's nonce.** `I_A` is secret from the attacker and may be known
  only by `A` and `B`.
- **Secrecy of B's nonce.** `I_B` is secret from the attacker and may be known
  only by `A` and `B`.
- **A's injective agreement with B.** `A` is the asserter and `B` is the
  subject of injective agreement on `(A, B, I_B)`.
- **B's injective agreement with A.** `B` is the asserter and `A` is the
  subject of injective agreement on `(A, B, I_A)`.

Listing a goal in the open-admission scenario means that it is tested there;
it does not assert the verdict in advance.
